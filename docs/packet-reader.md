# Packet reader

The Windows companion reads Odyle from the game's own network traffic and publishes it to the paired account. It never accepts typed values. Readings carry the adapter name `global-reference-v1`; the backend stores a reading only when its registry (`backend/pb_hooks/lib/protocols.cjs` in the dashboard repository) lists that name, so an outdated or unknown client cannot write totals.

## Local operation

Install [Npcap](https://npcap.com/#download) separately. The app loads its installed library from the Windows system Npcap directory; no driver is bundled or installed automatically. **Settings → Packet reader** shows whether Npcap is installed (its `System32\Npcap\wpcap.dll` or its `HKLM\SOFTWARE\Npcap` registry key) each time Settings opens, with the download link. Restricted Npcap installations may require capture permissions. Pair the app to your dashboard account; the reader then starts by itself whenever the app connects. **Keep Odyle running before logging the character into the game** when you can: the login snapshot names the character and both Odyle components at once. A reader started later still reads the total from the next live Odyle change, but needs one relog or channel change before the game names the character it belongs to. An empty account can start detection immediately; no prior character record is needed.

The reader captures on every interface Npcap lists. A supervisor keeps one capture worker per interface: an interface that fails or stops delivering packets (an adapter reset or removed, a broken capture) is opened again after 5 seconds, then 10, 20, 40 and at most 60 seconds while it keeps failing; the interface list is read again every 30 seconds, so a VPN, a game accelerator or a reset network card that appears later is captured too; and when Windows resumes from sleep every worker restarts. Interfaces that cannot be opened at all (Bluetooth, WAN miniports) are normal and do not count as a problem while another interface captures; the reader line shows a problem only when no interface can capture. Failures, recoveries, new interfaces and resumes are written to the log.

Npcap receives incoming TCP traffic from game port 13328. Before decoding a packet, the app checks that its IPv4 connection belongs to a process named AION2/AION-2 using the operating system's connection table, not game memory. Other processes and the game's HTTPS/login connections are ignored. The discovery filter stays open across reconnects so the initial handshake and snapshot are not lost to the two-second connection refresh. Ethernet, raw IPv4 and loopback link types are supported; IPv6, IP fragmentation, UDP, unsupported frame variants and encrypted payloads are not. It cannot decrypt or bypass game protection.

Packet bytes remain in bounded in-memory buffers. The app does not save or upload raw traffic and never injects packets. Streams with malformed framing, conflicting retransmissions or a missing segment that does not arrive within three seconds are blocked until the connection changes, and the reader line says so (**Unsupported or incomplete packets** or **Game packets were lost on the way**). Only bytes that reach a decoder count as game traffic, so a blocked connection no longer keeps a value live: 20 seconds without decodable bytes mark the reading stale like a closed game. `Odyle.Core.GameStreams` holds the per-connection reassembly and decoding, which the Core checks exercise. A midstream start waits for a complete protocol heartbeat to establish framing; it cannot recover the snapshot or identity that already passed. Live `0C61` updates carry the current total, so the value appears at the next Odyle change, and the reader shows **Started after login** until then. A snapshot sent later on the same connection is read as well. A new game connection clears the warning, and the closing packets of an old connection (FIN, RST or an empty ACK) never open a new stream. A changed own-character ID clears the Odyle owner and starts identifying the new character; an initial or repeated identity message alone is not a switch.

## What is published and when

* A reading belongs to the character the game names, never just to the selected one. A snapshot is held until its owner is known: an own-character message that arrives next claims it, and after a character switch (often on a new connection, with the snapshot before the identity) the previous character never receives the new one's value. With no new identity after five seconds the snapshot goes to the current character, unless its stat owner differs from the one that character had; then the app waits up to 30 seconds for the game to name it. Live updates keep the owner of their snapshot. A value read before any snapshot or identity (a start after login) is shown on the card but not saved until the game names the character, which it does at the next login or channel change; a reading never attributed to a character is dropped when the game connection changes.
* Odyle is sent the first time a character's value is known and afterwards only when it changes. The 20-second presence heartbeat keeps an unchanged value live on the dashboard; it turns stale 45 seconds after the heartbeat stops.
* No decodable game packets for 20 seconds (the game closed, or its connection blocked by lost packets), stopping the reader, switching characters, disconnecting or quitting marks the reading stale on the server; the last value is kept. Odyle restarting itself for an update or a language change is the exception: the live character, its last reading and stat owner are handed to the new start (`handover.json`, valid for a minute, same server and account), which sends that reading again under its own session and keeps attributing live updates to the character, so the heartbeat keeps it live without a relog. A game that stopped meanwhile sends nothing, and the reading turns stale after 20 seconds as usual.
* A duplicate of the same frame seen on a second capture interface is ignored. A server refusal (unknown adapter, expired session) shows **Not saved** with the server's message and retries after a minute; an expired publisher session is rotated automatically. A server that asks the app to slow down (429) pauses sending until its `Retry-After` without rotating the session, so the reading stays live.

The card shows the total only, the game's two numbers added together; below it a line appears only while something needs attention, such as a refused save.

## Automatic character setup

Every decoded Odyle update, each distinct stat frame layout (once per run) and every own-character message are written to the log (`%LOCALAPPDATA%\Odyle\logs\odyle.log`) as decoder diagnostics, with their numbers but no packet payloads; individual frames are not.

The independently implemented `3336` own-character decoder reads a varint ID, four-byte mask, one-byte mask, UTF-8 byte count and name, little-endian server ID and class ID. A valid name with a known Global server/region is saved via the metadata-only API and selected automatically. Repeated messages are deduplicated; account-owned records are reused. The class is a structural check, not a stored profile field. Raw identifiers and packet payloads are not sent to the backend.

Global server IDs encode faction, region and server number. The name/ID facts come from the public [Global server table](https://github.com/cyberbadger6969/aion2-dps-meter/blob/main/data/servers.json), and identity fields from its [protocol documentation](https://github.com/cyberbadger6969/aion2-dps-meter/blob/main/src/AionMeter.Core/Protocol/PacketParser.cs). For example, `2304` maps to Lumiel / Global EU. Unknown mappings, malformed text and unnamed tutorial characters do not produce an account record, and their readings are not saved; the app has no manual character entry.

## Wire format

The decoder follows public wire-format observations: length varints, optional `F0`–`FE` transport flags, `FF FF` LZ4 blocks, snapshot `0B 61`, update `0C 61`, and own identity `33 36`. Snapshot frames can contain two explicit values, or the single-value form with an implicit zero base. Update frames come in two forms and neither needs a preceding snapshot: the single-value form carries the new total (the reference project measured base 40 + bonus 600, a spend of 80 and a packet value of 560), which is all the card shows; the two-value form repeats base and bonus. An increase ends with a flag byte and a 32-bit delta, a decrease with one byte; other trailers produce no total. The update opcode is shared with other counters that differ only in their stat-owner id, so the owner is taken from a snapshot whenever one has been seen on this run or an earlier one. The numeric owner ids are kept per account in `%LOCALAPPDATA%\Odyle\stat-owners.json` and never sent anywhere. Without any known owner, the first id seen on a connection is adopted until a snapshot replaces it. The reference project observed the stat-owner id to be fixed per account across characters and sessions, while the own-identity message carries a per-session id, so the two are never compared. Ambiguous snapshots and unknown layouts produce no total. Sprint/dash fields and other stat IDs are ignored without disturbing the Odyle owner.

References: [Aion2 Aether Monitoring](https://github.com/gyu98-mun/Aion2_Aether_Monitoring/blob/main/aion2_core.py) (format observations; its source has no reusable license and was not copied), [AionMeter for Global](https://github.com/cyberbadger6969/aion2-dps-meter) (Global port, heartbeat framing and transport flag; GPL source not incorporated), [Npcap API](https://npcap.com/guide/npcap-devguide.html) through native imports, and [K4os LZ4](https://github.com/MiloszKrajewski/K4os.Compression.LZ4) as the only managed dependency.

## Live evidence

On 2026-10-13 the passive diagnostic ran against the author's own AION2 client, Steam build **25800038**, EU Global / Lumiel, with Npcap **1.10.7**. It decoded live heartbeat and gameplay frames, and after a relog observed `0B61` with a 487-byte payload and extracted **0 + 390 = 390**, matching the two values shown in the game. Live `0C61` frames with eight-byte payloads carried stat field 12, not the Odyle field 1; they are ignored without erasing the owner. The live-update path for field 1 follows the documented format, including the reference project's finding that its single value is the new total, but has not yet been compared on Global against an in-game spend or recharge: if the number on the card ever differs from the game, note the game value, the card's `base + bonus` and the time, and open an issue. No raw payloads, network endpoints, player identifiers or account data were retained.

Synthetic checks cover reordered/fragmented TCP, duplicate and conflicting overlaps, sequence rollover, heartbeat synchronization, flagged frames, framing/decompression bounds, single/two-component snapshots, ambiguous snapshots, single-value and two-value updates with and without a snapshot, owner adoption and trusted owners, a flagged update after a midstream heartbeat, repeated and changed own identities, and the UI/API publishing path against a disposable backend.
