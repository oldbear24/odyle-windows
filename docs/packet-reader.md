# Packet reader

The Windows companion reads Odyle from the game's own network traffic and publishes it to the paired account. It never accepts typed values. It only listens to the player's own game connection: it never reads game memory, changes or sends game traffic, automates play or collects combat data or other players' data. The installer's welcome page and **Settings → Packet reader** show this scope notice, with the note that Odyle is an unofficial fan project, not affiliated with or endorsed by NCSOFT, whose rules ban unauthorized programs, so it is used at the player's own risk. Readings carry the adapter name `global-reference-v2`; the backend stores a reading only when its registry (`backend/odyle/protocols.go` in the dashboard repository, or the adapters added under the superuser **Server controls**) lists that name, so an outdated or unknown client cannot write totals. Each stored history row records the adapter that decoded it.

**Deploy order.** A push to `main` here ships the app to every user at once, so a release that changes the adapter name may only be pushed after the backend that accepts the new name is deployed. For v2: deploy the dashboard backend that lists `global-reference-v2` (it keeps `global-reference-v1` for apps not yet updated), then push this version. Server controls can switch either adapter off without a deploy, which is the kill switch for a decoder that turns out wrong. When the backend refuses a reading because it does not list the adapter (*This packet adapter has not been validated for Global. No reading was saved.*), the app looks for an update at once instead of at its daily check, and at most once an hour after that. The card says **Odyle needs an update to keep reading**, with **Restart to update** once the new version is downloaded, instead of repeating the server's message, and the reading is tried again quietly every ten minutes in case the server takes the adapter back.

**Reader pause.** Switching an adapter off only refuses its readings; the apps keep capturing. **Server controls → Pause packet readers** goes further: the rooms, session and heartbeat answers carry `readerPaused`, so every paired app that knows the switch stops capturing and closes Npcap within about 20 seconds, and a reading sent meanwhile is refused with 503 *Packet readers are paused by the server operators.*, which the app treats the same. The card shows **Paused by the server** with the operators' announcement, **Start** stays off, and the heartbeat keeps running; when the switch is off again, the reader starts by itself (unless it was stopped by hand). Builds from before the switch keep capturing, and their readings are refused.

## Local operation

Install [Npcap](https://npcap.com/#download) separately, with its default options. The app loads its installed library from the Windows system Npcap directory; no driver is bundled or installed automatically, since Npcap's free license does not allow it. The installer checks for `HKLM\SOFTWARE\Npcap` in both registry views and, when it is missing, shows a page with a button and a last-page checkbox that open the download page. The app checks at every start (its `System32\Npcap\wpcap.dll` or the registry key) and whenever the reader cannot start. Missing, not loading or showing no capture interface, the reader line says so with an **Install Npcap ↗** (or **Npcap setup ↗**) link instead of a footer message, and Npcap is looked for every 10 seconds: once it works, the reader starts by itself. Npcap installed with **Restrict Npcap driver's access to Administrators only** (its `AdminOnly` option under `HKLM\SYSTEM\CurrentControlSet\Services\npcap\Parameters`) lists no interface to an Odyle without administrator rights; the reader line and **Settings → Packet reader**, which shows the check each time Settings opens, name that option, and reinstalling Npcap without it fixes it. Pair the app to your dashboard account; the reader then starts by itself whenever the app connects. **Keep Odyle running before logging the character into the game** when you can: the login snapshot names the character and both Odyle components at once. A reader started later still reads the total from the next live Odyle change; the game names the character it belongs to within a few minutes (it repeats the own-character message irregularly: in the author's log half the repeats came within about 90 seconds, a quarter only after more than four minutes and the longest after about 45 minutes), or at once after a relog or channel change. An empty account can start detection immediately; no prior character record is needed.

The reader captures on every interface Npcap lists. A supervisor keeps one capture worker per interface: an interface that fails or stops delivering packets (an adapter reset or removed, a broken capture) is opened again after 5 seconds, then 10, 20, 40 and at most 60 seconds while it keeps failing; the interface list is read again every 30 seconds, so a VPN, a game accelerator or a reset network card that appears later is captured too; and when Windows resumes from sleep every worker restarts. Interfaces that cannot be opened at all (Bluetooth, WAN miniports) are normal and do not count as a problem while another interface captures; the reader line shows a problem only when no interface can capture. Failures, recoveries, new interfaces and resumes are written to the log.

Npcap receives incoming TCP traffic from game port 13328. Before decoding a packet, the app checks that its IPv4 connection belongs to a process named AION2/AION-2 using the operating system's connection table, not game memory. A dual-mode socket connected to an IPv4 server is listed in the IPv6 table with IPv4-mapped addresses (`::ffff:a.b.c.d`); its packets are IPv4, so such a row counts as an IPv4 connection. Other processes and the game's HTTPS/login connections are ignored. The discovery filter stays open across reconnects so the initial handshake and snapshot are not lost to the two-second connection refresh. Ethernet, raw IPv4 and loopback link types are supported; IPv6, IP fragmentation, UDP, unsupported frame variants and encrypted payloads are not. It cannot decrypt or bypass game protection.

When an AION2 process runs but no IPv4 connection of it to port 13328 shows up for about a minute, the reader looks at the connection tables once every 15 seconds (IPv4 and IPv6, connection metadata only, nothing is decoded) and the waiting line says why when it can: **AION2 connects to the game server over IPv6**, **The game connection runs through &lt;program&gt;, not AION2** (an accelerator, a proxy or a renamed client holds the connection to the game port), or **AION2 is connected, but not on the game port 13328** with the ports it uses (web ports 80 and 443 do not count). Otherwise it keeps waiting for the game connection. **Settings → Troubleshooting → Copy diagnostics** puts the version, the Npcap check, the capture interfaces, the reader's last status lines and the end of the log on the clipboard for a bug report, with the account id, the PC's name and the Windows user folder masked; character names and the server's host stay in.

Packet bytes remain in bounded in-memory buffers. The app does not save or upload raw traffic and never injects packets. A missing segment that does not arrive within three seconds, a conflicting retransmission or bytes that do not frame **resync** that connection instead of stopping it: reassembly starts again at the next segment, and the decoder waits for the next protocol heartbeat, as after a midstream start, keeping the character it knows and the reading on the card. The lost bytes may have held a character switch (the new character's snapshot and identity), so the next reading after a resync waits for the game to name its character like a snapshot, and an unnamed snapshot no longer goes to the named character after 30 seconds. The reader line says **Game packets were lost on the way · resyncing with the game…** or **Unreadable game packets · resyncing with the game…**, then **Back in sync with the game** once a heartbeat is found; a live reading keeps its live line meanwhile (the log notes the resync). A value that changed inside the lost bytes shows again at the next Odyle change. More than five resyncs within a minute block the connection until it closes, with **Unsupported or incomplete packets**, so a changed protocol shows up as a problem instead of a loop. Only bytes that reach a decoder count as game traffic, so a blocked connection no longer keeps a value live: 20 seconds without decodable bytes mark the reading stale like a closed game. `Odyle.Core.GameStreams` holds the per-connection reassembly, resync and decoding, which the Core checks exercise. A heartbeat (`06 00 36`, or the 11-byte `0E 00 36` form) is trusted as a frame boundary only when the frame after it starts with a valid length; three matching bytes inside a payload are not enough. Until the next heartbeat confirms that boundary, a frame claiming more than 64 KB means the match was payload: the scan goes on from the next byte instead of waiting for up to 1 MB of stream. A midstream start cannot recover the snapshot or identity that already passed. Live `0C61` updates carry the current values, so the value appears at the next Odyle change, and the reader shows **Started after login** until then. A snapshot sent later on the same connection is read as well. A new game connection clears the warning, and the closing packets of an old connection (FIN, RST or an empty ACK) never open a new stream. An own-character message with another character ID is a character switch, also when its name, server or class cannot be read (a class or server this build does not know): the new character then stays unnamed, and nothing is saved for it until a readable message names it, instead of its value going to the previous character. A short `3336`, one without a readable ID and a repeat of the same ID change nothing.

## What is published and when

* A reading belongs to the character the game names, never just to the selected one. The game sends a snapshot whenever it loads a character into the world (login, character switch, teleport, channel change) and names the character only once the loading screen ends, 6 to 10 seconds later. A snapshot is therefore held until that own-character message claims it, however long the loading takes, so after a switch the previous character never receives the new one's value. Only a snapshot still unnamed after 30 seconds, one sent without loading a character, goes to the named character, and only if that character's Odyle was already read this run and no game connection resynced since; a character that never had a reading, such as one without Odyle, never receives it. When two capture interfaces see the same connection, each reports the switch; the second report is ignored once the game has named the new character. Live updates keep the owner of their snapshot; an update read while no character owns the reading goes to the named character after five seconds. A value read before any snapshot or identity (a start after login) is shown on the card but not saved until the game names the character, which it does within a few minutes or at the next login or channel change; a reading never attributed to a character is dropped when the game connection changes.
* A character without Odyle: when a full stat snapshot the decoder understood whole (at least 32 records; Global's carry 73) has no Odyle record, the character the game names next shows **No Odyle on &lt;name&gt; yet · it may unlock at level 22** instead of waiting for a snapshot forever (level 22 is what players report, not something the packets say). Nothing is sent for it; its first Odyle reading replaces the note.
* Odyle is sent the first time a character's value is known and afterwards only when it changes. The 20-second presence heartbeat keeps an unchanged value live on the dashboard; it turns stale 45 seconds after the heartbeat stops.
* No decodable game packets for 20 seconds (the game closed, or its connection blocked after repeated resyncs), stopping the reader, switching characters, disconnecting or quitting marks the reading stale on the server; the last value is kept. Odyle restarting itself for an update or a language change is the exception: the live character and its last reading are handed to the new start (`handover.json`, valid for a minute, same server and account), which sends that reading again under its own session and keeps attributing live updates to the character, so the heartbeat keeps it live without a relog. The handed-over reading keeps the adapter name that read it, also across the update to v2; a server that no longer accepts that adapter drops it without asking for an update, and the new decoder reads the next Odyle change. A game that stopped meanwhile sends nothing, and the reading turns stale after 20 seconds as usual.
* A duplicate of the same frame seen on a second capture interface is ignored. A server refusal (expired session, an outdated reading) shows **Not saved** with the server's message and retries after a minute; an expired publisher session is rotated automatically. A refused adapter asks for an update as described above. A server that asks the app to slow down (429) pauses sending until its `Retry-After` without rotating the session, so the reading stays live.

The card shows the total only, the game's two numbers added together; below it a line appears only while something needs attention, such as a refused save.

## Automatic character setup

Every decoded Odyle update and stat snapshot (its size, record count and Odyle record with tag, values and offset, or that it has none), each other stat resource that sends updates and each distinct stat frame layout (once per run), and every own-character message (name, server and class ID) are written to the log (`%LOCALAPPDATA%\Odyle\logs\odyle.log`) as decoder diagnostics, with their numbers but no packet payloads; individual frames are not.

The independently implemented `3336` own-character decoder reads a varint ID, four-byte mask, one-byte mask, UTF-8 byte count and name, little-endian server ID and class ID. A valid name with a known Global server/region is saved via the metadata-only API and selected automatically. Repeated messages are deduplicated; account-owned records are reused. The class is a structural check, not a stored profile field: class IDs 5 to 48 are accepted, which includes 45 to 48, the IDs the reference decoder maps to the Brawler (not yet confirmed with a Global capture; the log shows the class ID of every character). Raw identifiers and packet payloads are not sent to the backend.

Global server IDs encode faction, region and server number. The name/ID facts come from the public [Global server table](https://github.com/cyberbadger6969/aion2-dps-meter/blob/main/data/servers.json), and identity fields from its [protocol documentation](https://github.com/cyberbadger6969/aion2-dps-meter/blob/main/src/AionMeter.Core/Protocol/PacketParser.cs). For example, `2304` maps to Lumiel / Global EU. Region digits 1 and 2 are both North America and read as `GLOBAL_NA` with the same server names, so an NA-East and an NA-West server with the same number show the same name until the NA-West server list is known. Unknown mappings, malformed text and unnamed tutorial characters do not produce an account record, and their readings are not saved; the app has no manual character entry.

## Wire format

The decoder follows public wire-format observations: length varints, optional `F0`–`FE` transport flags, `FF FF` LZ4 blocks (a block restoring more than 8 MB is skipped whole), snapshot `0B 61`, update `0C 61`, and own identity `33 36`.

Both stat frames are built from the same **stat record**: a tag byte, the stat's resource ID as a little-endian 32-bit number, then the base value as a varint when the tag has bit 4 and the bonus value when it has bit 8. A value the tag leaves out is zero: `0C` carries base and bonus, `08` the bonus only, `04` the base only and `00` neither. Odyle is the record of resource **60000001** (bytes `01 87 93 03`); resource 80000001 (`01 B4 C4 04`) is another, small counter that never counts as Odyle. The reader reads no other resource, whatever its shape, so no per-account owner has to be learned: the `stat-owners.json` of earlier builds is no longer used and is removed at start.

* The snapshot `0B61` is a varint record count followed by the records (73 on the author's characters). When the whole layout is walked record by record, its Odyle record is read; when an unknown tag stops the walk, the Odyle record is searched for by its resource ID after a valid tag. Several Odyle records that disagree, and totals above 1,000,000, are not read. Only a snapshot walked whole without an Odyle record counts as a character without Odyle.
* The update `0C61` is a direction byte, one record and a trailer: an increase (direction 1) ends with a flag byte and a 32-bit delta, a decrease or a regeneration tick (direction 0) with one byte; other trailers produce no total. An update carries the new base and bonus, so it needs no snapshot first. Regeneration adds 15 to the base every three hours (UTC hours 1, 4, 7 and so on) and arrives as a two-value update; spending drains the base before the bonus, so an update with the bonus only equals the total the next snapshot shows.

Sprint/dash fields and other stat IDs are ignored without disturbing the Odyle reading.

References: [Aion2 Aether Monitoring](https://github.com/gyu98-mun/Aion2_Aether_Monitoring/blob/main/aion2_core.py) (format observations and the resource ID 60000001; its source has no reusable license and was not copied), [AionMeter for Global](https://github.com/cyberbadger6969/aion2-dps-meter) (Global port, heartbeat framing, transport flag and class IDs; GPL source not incorporated), [Npcap API](https://npcap.com/guide/npcap-devguide.html) through native imports, and [K4os LZ4](https://github.com/MiloszKrajewski/K4os.Compression.LZ4) as the only managed dependency.

## Live evidence

On 2026-10-13 the passive diagnostic ran against the author's own AION2 client, Steam build **25800038**, EU Global / Lumiel, with Npcap **1.10.7**. It decoded live heartbeat and gameplay frames, and after a relog observed `0B61` with a 487-byte payload and extracted **0 + 390 = 390**, matching the two values shown in the game.

The decoder log of 2026-10-14 and 15 (same client and server) confirms the live-update path: single-value `0C61` updates of Odyle equalled the total of the snapshot that followed, spends and regeneration ticks (for example 15 + 895 after the tick) matched the game, and the snapshots after a teleport (494 to 503 bytes) held Odyle and the second counter (3 + 1, later 2 + 1). The earlier adapter `global-reference-v1` found Odyle by byte patterns and logged it as "owner 51591", the second counter as "owner 74292": both are the varint misreads of the 32-bit resource IDs after their first byte, which is why v2 reads the records by resource ID instead. Odyle records with tag `04` (no bonus) or `00` (nothing) have not been seen on Global yet; they follow the same record format. If the number on the card ever differs from the game, note the game value, the card's value and the time, and open an issue with the decoder lines of the log. No raw payloads, network endpoints, player identifiers or account data were retained.

Synthetic checks cover reordered/fragmented TCP, duplicate and conflicting overlaps, sequence rollover, heartbeat synchronization and false heartbeat matches, resync after a lost segment, a conflicting retransmission and broken framing, the resync limit, flagged frames, framing/decompression bounds and oversized bundles, stat records of every tag, snapshots in the logged shapes (two Odyle-shaped fields, 0 + 390, 15 + 940, 90 + 990, a lone second counter, unwalked layouts), updates in the logged shapes (regeneration, spends, increases, the second counter), randomized stat layouts and randomized frames and streams that must never throw, repeated, short and changed own identities, unreadable identities with another ID, short snapshots without Odyle, a scanned boundary before an oversized frame, IPv4-mapped connection-table rows, Brawler class IDs, and the UI/API publishing path including a character without Odyle and a refused adapter.
