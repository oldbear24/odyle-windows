# Odyle Windows Companion

A .NET 10 WPF tray app for your **Discord-linked Odyle account**, persistent characters and private PocketBase rooms. The dashboard and backend are in [odyle-dashboard](https://github.com/oldbear24/odyle-dashboard). The app speaks **English and Czech**.

## Use it

1. Start/configure the dashboard's backend and sign in on the web with Discord.
2. Download the newest release: **My rooms & characters** links it as **Windows app &lt;version&gt;**, and the **Pair Windows app** dialog offers the packages (see [Download and updates](#download-and-updates)). The simplest is the installer `odyle-<version>-win-x64-setup.exe`: it needs no administrator rights. Alternatively extract a ZIP into a folder you can write to and run `Odyle.exe`. Either way the app updates itself from then on.
3. On **My rooms & characters**, choose **Pair Windows app**, then **Copy connection link**.
4. Open **Settings** (⚙) and click **Paste link & connect**. Settings opens by itself until the app is paired. The link includes the server address and a one-use code that expires after five minutes. You pair once: the app then stays connected across restarts, updates and weeks switched off, until you choose **Disconnect**, remove the PC on the dashboard or choose **Sign out everywhere** there. You can also paste it into the input and press Enter. An older code-only connection works through the collapsed **Server address** option.
5. Install Npcap from its official site; **Settings → Packet reader** shows whether it is installed. The reader starts by itself once the app is connected to your account (**Stop**/**Start** beside the reader status toggles it). Keep Odyle running before logging your character into the game when you can: the login snapshot names the character at once. Started later, the app reads the total at the next Odyle change and asks for one relog or channel change so the game names the character. Odyle restarting itself (an update or a language change) is not such a late start: the character it was reading is handed to the new start and stays live without a relog. The character always comes from the game: its own-character message provides the name, server and Global region, and the app saves and shows that character automatically, following any in-game switch. There is no character picker or manual character entry; a character on a server the app cannot map yet is shown but not saved.
6. Rooms and sharing are set on the dashboard: under **My rooms & characters → Room sharing**, switch on each room that should see each character (**Manage rooms & sharing ↗** in Settings opens it). Sharing is per character: a new character starts private. Create and join rooms there too. The app picks up changes by itself. Values remain saved when you leave a room or sign out.

The app remembers your connection using Windows DPAPI, never Discord passwords or OAuth tokens. Pairing gives this PC its own device key; the app trades it for a fresh seven-day account token whenever it starts, once a day while it runs and whenever the server turns a token down, so the pairing never runs out on its own. Pairing and every sign-in send the PC's Windows computer name (at most 40 characters), so the dashboard's **Account & data** lists your paired PCs by name and lets you remove one; a removed PC notices within about a minute and asks for a new connection link. **Disconnect** forgets the device key on this PC and on the server. Only when the server no longer knows the key (Disconnect, PC removed, **Sign out everywhere**, account deleted) does the app ask for a new link; a `session.bin` that this Windows account cannot read counts as not paired too, with a message saying so. An app paired before device keys existed receives its key the next time it connects to an updated backend. Hosted connections require HTTPS; HTTP is allowed only on localhost.

**When the server is unavailable** the pairing is kept and the app tries again by itself: after 15 seconds, 30 seconds, 1 minute, 2 minutes and then every 5 minutes, counting down to the next try in the footer; **Reconnect saved account** (Settings → Server address) tries at once. A server that asks the app to slow down (429) pauses all requests for its `Retry-After` (a minute without one) and the footer shows **Server busy · retrying in …**; the reading stays live and the reader session is kept. While the app runs, a connection lost to the server is restored with the next 20-second heartbeat.

The main window is a compact 280 px card with a dark title bar and its own icon: the character the game reports, its current Odyle, reward cubes at the cost of the first room it is shared in, a Live / Stale / Saved state, the reader status and **Start/Stop reader**. Below it, **Online in your rooms** lists the other members' characters each of your rooms can see while their readers report them: Odyle, cubes at that room's cost, and an amber dot once a reading has gone stale. Offline characters and your own are left out. The list refreshes every 15 seconds while the window is open. The separate **Settings** window (⚙ or the tray menu) holds only what belongs to this PC: pairing and server address, account and disconnect, a read-only summary of where each character is shared, the Npcap check, how the window is shown (stay on top, checklist beside the card, start with Windows), notifications, the language, the installed version with its updates and the log folder. Everything else is configured on the dashboard. Closing either window keeps the app in the tray; starting Odyle again while it runs brings its window forward.

**Stay on top and your checklist.** The pin in the header keeps the window above other windows, for example the game in windowed or borderless mode; the tray menu and **Settings → Window** toggle the same. The checklist button beside it opens a panel to the right of the card with your **Daily & weekly** tasks from the dashboard: each list shows how many are done, a progress bar and a countdown to its reset (the Global service resets daily at 07:00 UTC and weekly on Wednesday; the backend's settings decide, and the header tooltip shows the reset in your local time). Tick a task when it is done; the server stores the time and the task unchecks itself at the reset. Tasks are added, renamed and removed on the dashboard (**Manage ↗**), and the panel refreshes every 15 seconds while the window is open. When the window grows it is kept on its screen. The window reopens where you left it, as long as that spot is still on a connected screen; otherwise it opens centred.

**Start with Windows.** **Settings → Window → Start with Windows** adds the per-user entry `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` → `Odyle` = `"<path>\Odyle.exe" --tray` (the installer offers the same). Started that way, Odyle waits in the tray: a paired app does not open any window, also while it is still retrying an unavailable server, and an unpaired one opens the window and settings as usual.

**Notifications.** With **Settings → Notifications → Remind me of planned runs** (on by default), Odyle shows a Windows notification 15 minutes before each planned run you joined on the dashboard, with the dungeon, the room, the local start time and the note; each run is announced once per start time, so a run moved to another time is announced again. The rooms are refreshed every minute while Odyle waits in the tray, so reminders work without the window. A downloaded update is announced once per version. Clicking a notification opens the window.

**Language.** Odyle follows the Windows display language: Czech on a Czech Windows, English otherwise. **Settings → Language** chooses Automatic, English or Čeština; the choice applies when Odyle restarts (Settings offers **Restart now**). Numbers, dates and times follow the chosen language, and the server's English messages are shown in Czech too, in the dashboard's wording.

**Announcements.** When the server's operators post a message (planned maintenance, an update to install), it appears above the reading card within 15 seconds, amber for warnings. ✕ hides it until the message changes.

All of these choices (window, position, language, notifications) are remembered on this PC in `%LOCALAPPDATA%\Odyle\preferences.json`; nothing about them is sent to the server.

**Log.** For troubleshooting, Odyle keeps a small log in `%LOCALAPPDATA%\Odyle\logs\odyle.log` (about 1 MB, plus the previous file as `odyle.previous.log`): start-up, connection and reader changes, errors, update actions and the decoder's diagnostics for Odyle updates, stat snapshots, frame layouts and the own-character message. It never contains account tokens, device keys or pairing codes. **Settings → Updates → Open log folder** opens it. An unexpected error is logged and the app keeps running with a short note.

## Download and updates

Every push to `main` that changes more than documentation publishes a [GitHub release](https://github.com/oldbear24/odyle-windows/releases/latest); the dashboard links the newest one on **My rooms & characters** and in its **Pair Windows app** dialog (its backend reads the release list from GitHub for it).

| Package | Approximate size | Requirements |
| --- | --- | --- |
| `odyle-<version>-win-x64-setup.exe` | 60 MB | Windows x64 (also Windows 11 on ARM through x64 emulation). Installs the self-contained build for the current user into `%LOCALAPPDATA%\Programs\Odyle`, no administrator rights |
| `odyle-<version>-win-x64.zip` | 300 KB | [.NET 10 Desktop Runtime](https://dotnet.microsoft.com/en-us/download/dotnet/10.0) for Windows x64 |
| `odyle-<version>-win-x64-self-contained.zip` | 68 MB | Bundles its runtime |
| `odyle-<version>-win-arm64.zip` | 300 KB | .NET 10 Desktop Runtime for Windows Arm64 |
| `odyle-<version>-win-arm64-self-contained.zip` | 63 MB | Windows on ARM, bundles its runtime |

Every file has a `.sha256` beside it. The installer adds a Start-menu shortcut and, if you choose, a desktop shortcut and **Start with Windows**; it is offered in English and Czech, and uninstalling (Settings → Apps) removes the program, its downloaded updates and the Start with Windows entry while keeping your pairing and preferences in `%LOCALAPPDATA%\Odyle`. For a ZIP, extract it into a folder you can write to (your own folder, not Program Files) and run `Odyle.exe`. The small download uses the installed runtime; Microsoft shows the required runtime download dialog if it is missing. Choose **Desktop Runtime**, which includes WPF support. Use a standalone package if you prefer no runtime installation. Sizes refer to this build and may change slightly.

**The app updates itself.** A released build (version `<Version>.<run number>`, for example 0.6.0.12) checks this repository's GitHub releases a few seconds after every start and then once a day while it runs (a check that fails, for example before the network is up, is retried within the hour); **Settings → Updates** shows the installed version with **Check now** and a link to the releases. When a newer release has a package of the same kind (small or self-contained) for this CPU (x64 or Arm64), the app downloads it to `%LOCALAPPDATA%\Odyle\updates\<version>`, verifies the ZIP against the release's `.sha256` file, extracts it and checks that the extracted `Odyle.exe` carries that version; the installer is never used for updates, and an installed app updates from the self-contained x64 ZIP like any other. The footer and Settings then offer **Restart to update**, and a notification says so once; left alone, the downloaded version installs by itself the next time Odyle starts. Installing moves the running `Odyle.exe` aside as `Odyle.exe.old` (Windows lets a running program be renamed but not overwritten), copies the new files into the same folder and starts the new version, which deletes the old file. The reader pauses for a moment only: a character that was live is handed to the new version, which sends its last reading again under its own session, so it stays live on the dashboard and your rooms without a relog. If the folder is not writable, Settings says so and the release page remains the way to update. Builds are unsigned: the checksum guards against a damaged download, not against a compromised release. Development builds (`dotnet run`, version without a run number) never replace themselves. For updates the app contacts `api.github.com` and `github.com` only, sending a standard request that names the app version; nothing about your account or characters is included.

**Readings come from the game only; manual entry is disabled in both clients and the backend.** While the reader runs, Odyle is sent to your account under the adapter name `global-reference-v1` when a character's value is first read and afterwards only when it changes. A 20-second heartbeat keeps the value live while decodable game packets keep arriving; the dashboard shows it as stale 45 seconds after the heartbeat stops. Each reading is saved to the character the game names: after an in-game character switch the new snapshot waits for the new character's identity, so it never overwrites the previous character. Stopping the reader, switching characters, 20 seconds without readable game packets, disconnecting or quitting marks the current reading stale while keeping the last value. If the server refuses a reading (for example a backend that does not list the adapter), the card shows **Not saved** with the server's message and the app retries a minute later. Close the window to keep it in the tray; **Quit** exits.

**How the reader works.** It passively decodes incoming IPv4/TCP game traffic owned by the local AION2 process using an existing Npcap installation: TCP reassembly, heartbeat synchronization, bounded framing, LZ4 blocks, the own-character message, the Odyle snapshot and live stat updates. It captures on every network interface Npcap offers, opens an interface again after it fails, picks up new ones (a VPN or game accelerator, a reset network card) within 30 seconds and restarts after the PC wakes from sleep; it reports a problem only when no interface can capture. A live EU Global / Lumiel check on Steam build 25800038 read the startup value **0 + 390 = 390**, matching the game display; the live-update path follows the same documented format and should be compared against the in-game number after a spend or recharge. Starting the reader **before** logging in is best: the login snapshot names the character and both Odyle components at once. Joining an established connection reads the total from the next live Odyle change and shows a hint to relog or change channel once so the game names the character. No game memory access, packet injection or gameplay automation is implemented. Npcap is installed separately and is not bundled. See [packet reader details](docs/packet-reader.md).

## Build and package

Windows 10/11 with .NET SDK 10:

```powershell
dotnet build src/Odyle.Reader/Odyle.Reader.csproj -c Release
dotnet run --project src/Odyle.Reader
dotnet run --project tests/Odyle.Core.Checks -c Release
dotnet run --project tests/Odyle.Reader.Checks -c Release
./scripts/publish.ps1
./scripts/publish.ps1 -SelfContained -Installer
./scripts/publish.ps1 -Runtime win-arm64
./scripts/publish.ps1 -Runtime win-arm64 -SelfContained
```

Packaging defaults to the small single-file executable and SHA-256 checksum. `-SelfContained` produces the separate standalone ZIP and stamps `SelfContained` into the assembly metadata, which the updater reads to fetch the same package kind. `-Runtime win-arm64` builds for Windows on ARM. `-Installer` (with `-SelfContained`, x64) also compiles [installer/odyle.iss](installer/odyle.iss) with Inno Setup 6 into `odyle-<version>-win-x64-setup.exe`, installing Inno Setup through Chocolatey when `iscc` is missing. Builds are unsigned. `-Version` stamps a version into the executable and the file names; a build with a four-part version is a release build and updates itself. The Core checks run on any OS; the UI checks and packaging need Windows.

Every push to `main` that changes more than `docs/`, Markdown files or `THIRD-PARTY.md` runs the checks and publishes the GitHub release `v<Version>.<run number>` (for example `v0.6.0.12`) with the installer, the four ZIPs and their checksums, marked as the latest release; installed apps pick it up from there, so keep the package names and the `.sha256` files as they are. `<Version>` comes from `Odyle.Reader.csproj`; bump it to start a new line. Manual runs of the release workflow, other branches and pull requests run the checks and upload every package as workflow artifacts without publishing.

`dotnet run --project tests/Odyle.Reader.Checks -c Release -- --update-probe` downloads the newest release's package for this machine into a temporary folder and verifies it the way the app does (needs the network). `-- --screenshots <folder>` renders the preview images.

The optional end-to-end check accepts a test server URL and **disposable desktop pairing code** as two arguments. Against a disposable backend that approves the synthetic `test-fixture-v1` adapter, it pairs, refreshes the account, saves packet zero, sends presence, invalidates freshness and confirms the value is retained. It does not delete characters or memberships.

Credentials (server address, account token and device key) are in `%LOCALAPPDATA%\Odyle\session.bin`, written whole or not at all like `preferences.json` and `stat-owners.json`. While Odyle restarts itself, `handover.json` holds the live character for the next start (its id, name and server number, the last Odyle total and its stat owner, no credentials); the next start removes it when it reads it and ignores one older than a minute or from another account. An older guest credential will fail the new account API and must be replaced by pairing from the Discord dashboard.

See [API contract](docs/api.md) and the dashboard's [Discord setup](https://github.com/oldbear24/odyle-dashboard/blob/main/docs/discord-setup.md). Live Discord sign-in requires the operator's provider configuration; it is never replaced by password registration.
